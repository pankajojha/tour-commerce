Tour Planner Platform — Current-State Architecture

Focus: service topology and database connectivity as actually configured today (docker-compose, Cloudflare Pages + Tunnel, external PostgreSQL, REST db-proxy with a domain-API layer). Reconstructed from source, env files, docker-compose, and Terraform deploy configs.

Reality vs. CLAUDE.md / design docs: The written design describes an all-AWS serverless target (Aurora Serverless v2, ElastiCache, CloudFront). The currently deployed state is a hybrid: an external self-hosted PostgreSQL at db.pankajojha.dev:5432 (Terraform module.database is "Secrets Manager only; no AWS RDS"), a REST/JSON db-proxy container fronting that DB (previously gRPC — now HTTP for simpler internet exposure), that proxy published to AWS through a Cloudflare Tunnel at db-proxy.exploreragents.com, and the two React UIs served from Cloudflare Pages with same-origin /api proxying. This document reflects the current state.
What changed since the last revision:
  • db-proxy is REST, not gRPC. Listens on :8090 (was :50051). GET /health + typed domain routes, plus unauthenticated /docs and /openapi.yaml.
  • The generic /query & /exec raw-SQL endpoints have been removed. All DB access now goes through typed /api/<project>/<action> endpoints — there is no longer a way to send raw SQL over the wire.
  • Domain-API layer, expanded. Projects: trips, auth, policy, cart, checkout, orders, payments, ai, and a large new aiapp (~50 endpoints: trip plans, members, sections, entries, versions, runs, events, outputs + legal-hold/retention, nonces, webhook callbacks, share tokens, system prompts). SQL is owned by db-proxy in internal/queries/*_query.go and bound server-side with pgx placeholders; callers POST parameters only, never SQL. Multi-statement flows (e.g. activate-prompt) run in a server-side transaction.
  • Go services deleted their SQL. trips/db/db.go, trips/lifecycle/lifecycle.go removed; trips, auth, policy handlers and every tour-commerce service now call db-proxy over HTTP. Their Open() returns an HTTP client, not *sql.DB. (policy/db/db.go still exists with a dead dbproxy-driver fallback but nothing imports it.)
  • tour-planner-ai routes through db-proxy too. Repositories (system_prompts, ai_runs, trip_plans, webhooks, redaction_vault) gained a dual path: when DB_PROXY_URL is set they call the typed /api/aiapp/* endpoints via the new AIAppClient and DATABASE_URL is unused; otherwise the original asyncpg SQL path runs. RLS set_config(user_id, …, is_local=true) can't persist across REST calls, so user scoping is best-effort in proxy mode. (The earlier generic DBProxyPool / bind_sql shim still ships but now targets removed endpoints.)
  • DB migrations V005 / V006 added (allow_two_open_trips, trip_entitlement_and_free_trip_limit); V001–V004 also revised. Commerce CDK moved to tour-agent-infra/infrastructure/commerce/ (the old tour-commerce/infrastructure/ was deleted).
  • Two auth gates on db-proxy. Client credentials (X-Client-Id/X-Client-Secret, defaults johnpankaj / exploreragents2findmytour — on by default) and an optional bearer token (Authorization: Bearer $DB_PROXY_API_KEY).
  • Cloudflare Tunnel exposure. cloudflared on host 192.168.1.133 publishes db-proxy.exploreragents.com → local :8090. TLS terminates at the Cloudflare edge; the LAN hop cloudflared→db-proxy is plaintext HTTP.
  • Client env vars changed: DB_PROXY_URL (+ DB_PROXY_API_KEY, DB_PROXY_CLIENT_ID, DB_PROXY_CLIENT_SECRET) replace the old DB_PROXY_ADDR/HOST/PORT trio (still accepted as fallbacks).

2. Services

tour-agent

Go 1.21 · Lambda

System of record. Sub-services: auth (8 handlers), trips, policy, ai-proxy. trips/policy/auth own no SQL — they call db-proxy domain APIs over HTTP.

db-proxy

Go · REST/JSON

Fronts external Postgres over HTTP on :8090. Typed domain API only (/api/<project>/<action>) — raw /query&/exec removed. All SQL lives in internal/queries/*_query.go; multi-statement flows run in a server-side transaction. Root docker-compose.yml.

tour-planner-ai

Python 3.11

Bedrock AgentCore. 9 specialist agents; MCP tools for catalogue reads. Its transactional repositories (trip_plans, ai_runs, webhooks, redaction_vault, system_prompts) call db-proxy /api/aiapp/* via AIAppClient when DB_PROXY_URL is set, else asyncpg.

tour-commerce

Go 1.21 · Lambda

cart · checkout · orders · payments · ai-commerce. Each service's db.go was rewritten — Open() now returns an HTTP client to db-proxy /api/{cart,checkout,orders,payments,ai}/*. Local CDK infrastructure/ removed; it now lives in tour-agent-infra/infrastructure/commerce/.

3. Database Connectivity (the important part)

One external PostgreSQL host db.pankajojha.dev:5432 holds logically separate databases (explorerdb for tour-agent, a commerce DB, and the Strapi DB). In production every tour-agent / tour-commerce service — and tour-planner-ai — reaches Postgres through db-proxy's typed domain API over HTTP; only db-proxy (and Strapi) hold a real connection pool. db-proxy internals

Pool & server

internal/dbpool builds a DSN (BuildDSN, or DATABASE_URL) and opens one pgxpool.Pool. internal/httpserver serves /health (pool.Ping) and registers the domain routes only — the raw /query//exec executors were removed. Per-request DB timeout 30s; graceful shutdown.

Domain API layer

internal/httpserver/domain{,_commerce,_aiapp}.go + internal/queries/ (trips, auth, policy, cart, checkout, orders, payments, ai, and aiapp — ~50 endpoints incl. trip plans, runs, outputs+retention, webhook callbacks, share tokens, system prompts). Each handler decodes a typed JSON struct and calls a query function using pgx placeholders. The only path to Postgres.

Auth (two gates)

Client credentials — X-Client-Id/X-Client-Secret (aliases client_id/secret), constant-time compared, enabled by default (johnpankaj / exploreragents2findmytour). Bearer token — Authorization: Bearer or X-Api-Key, only enforced if DB_PROXY_API_KEY is set (warns and runs open otherwise). /health, /docs, /openapi.yaml are public.

Cloudflare exposure

cloudflared on 192.168.1.133 maps db-proxy.exploreragents.com → http://192.168.1.133:8090. Edge terminates TLS (AWS→CF encrypted); cloudflared→proxy is plaintext HTTP on the LAN. Optional Cloudflare Access self-hosted app + service token for defence in depth.

Risks in current DB connectivity:
  • Injection surface is closed on the live path. Every serving endpoint (/api/*) binds params with pgx. Remaining risk is confined to orphaned code — policy/db/db.go's sqlLiteral and Python bind_sql / dbproxy_pool.py — which target removed endpoints and should be deleted before they're accidentally rewired.
  • No caller-side transactions / prepared statements. Atomicity now depends on db-proxy composing multi-statement work inside one query function (done for activate-prompt; each new cross-row flow needs the same treatment). tour-planner-ai's conn.transaction() is a no-op in proxy mode, so any repo method still doing multi-step work over the pool loses atomicity.
  • RLS scoping is lost in proxy mode. tour-planner-ai's per-connection set_config(request.user_id, …, is_local=true) can't persist across independent db-proxy calls — row-level security must be enforced inside db-proxy / upstream; the user_id set by get_connection() is best-effort only.
  • Boundary shift. tour-planner-ai now reads/writes trip_plans, ai_runs, webhooks etc. directly via /api/aiapp/*, not through tour-agent — CLAUDE.md still says the AI layer "must never own transactional state … calls tour-agent APIs via MCP tools". db-proxy is the new shared trust boundary; decide whether that's intentional.
  • LAN hop is plaintext. cloudflared → db-proxy (:8090) is HTTP; bearer token + DB creds travel unencrypted on that segment. Mitigated only if that host/LAN is trusted.
  • Weak default credentials, committed. DB_PROXY_CLIENT_ID/SECRET default to johnpankaj/exploreragents2findmytour in source; docker-compose.yml defaults the DB password to Passw0rd1; UI .env / .env copy files with live tokens are staged in find-my-tour-ui. DB_PROXY_API_KEY is optional and the service runs unauthenticated if unset.
  • Single points of failure. One external DB host (db.pankajojha.dev, shared with commerce + CMS) and now one db-proxy container in front of every Go service and tour-planner-ai.
  • Design drift: CLAUDE.md / design docs still promise Aurora + ElastiCache + CloudFront and Flyway-on-deploy; none back the DB today. A parallel db-gateway (nginx) design also exists in terraform/deploy/, unshipped — two competing "gateway" designs.

4. Request & Data Flow

  1. Browser → Cloudflare Pages. SPA loads from findmytour.ai / exploreragents.com; all API calls go same-origin to /api.
  2. Cloudflare Function proxy. functions/api/[[path]].js forwards /api/* to API_ORIGIN (API Gateway …execute-api…/production).
  3. API Gateway → Cognito JWT authorizer → Go Lambda (auth / trips / policy / ai-proxy). Caller identity from JWT sub.
  4. Lambda → db-proxy over HTTPS. The Lambda's DB client calls https://db-proxy.exploreragents.com/api/<project>/<action> with a bearer token + client credentials. Cloudflare edge → cloudflared tunnel → db-proxy REST :8090.
  5. db-proxy → PostgreSQL. db-proxy picks the matching query in internal/queries, binds parameters with pgx, and runs it on the shared pgxpool against db.pankajojha.dev (sslmode=require).
  6. ai-proxy → tour-planner-ai. Strict allowlist reverse proxy to AgentCore /invocations. The AI reads catalogue data via MCP tools, but persists its own state (trip_plans, ai_runs, webhooks, system_prompts) via db-proxy /api/aiapp/* when DB_PROXY_URL is set, else asyncpg.
  7. Commerce checkout calls tour-planner-ai for budget/conflict validation, writes bookings back through tour-agent, and persists cart/order/payment state via db-proxy /api/{checkout,orders,payments}/*.
  8. Strapi CMS always connects with its native PG client, bypassing db-proxy.

5. Solution Steps — Hardening & Aligning the Current State

Ordered, incremental. Each step is independently shippable and does not require the full AWS target migration.

  1. Rotate & remove committed secrets. Rotate the johnpankaj/exploreragents2findmytour client credentials and set non-default values via env; rotate the Passw0rd1 DB password; get the find-my-tour-ui/.env and .env copy files (with live Cloudflare tokens) out of the index and into .gitignore, scrub history.
  2. Make DB_PROXY_API_KEY mandatory. Fail startup instead of warning when it is unset, so the bearer gate can't silently be off in any environment.
  3. Encrypt the LAN hop. Either co-locate cloudflared and db-proxy so the plaintext hop is loopback-only, run db-proxy with TLS, or put both in the same Docker network with an internal TLS terminator. Add Cloudflare Access (service token) in front of the hostname.
  4. Delete the orphaned SQL clients. Remove db-proxy/driver/, policy/db/db.go, Python dbproxy_pool.py + bind_sql, and their tests — they interpolate SQL client-side and point at endpoints that no longer exist. Finish moving any remaining asyncpg repo method onto /api/aiapp/*.
  5. Audit multi-statement flows for atomicity. activate-prompt is transactional server-side; do the same for every checkout/order/override flow that touches more than one row, or add a session-token transaction API to db-proxy.
  6. Centralize config via Secrets Manager. Resolve DB_PROXY_URL + token + client creds (and the proxy's own DB creds) from Secrets Manager at startup instead of plaintext env / compose defaults.
  7. Observability. Wire the /health RPC into the container healthcheck (done in compose), emit pgxpool stats + structured request logs, and scrape them (CloudWatch / Prometheus). Add request IDs end-to-end.
  8. Remove the DB SPOF. PgBouncer or a read replica in front of db.pankajojha.dev; run db-proxy with ≥2 replicas behind the tunnel.
  9. Pick one gateway design. Decide between the REST db-proxy (shipped) and the nginx db-gateway (design-only in terraform/deploy/db-gateway/); delete the loser.
  10. Reconcile docs with reality. Update CLAUDE.md / design docs to describe the external-Postgres + REST-db-proxy + Cloudflare-Tunnel topology, or commit to the Aurora Serverless v2 target and delete the aspirational claims. One source of truth.
  11. Verify & test. Integration tests against the proxy (domain endpoints + /health), a smoke test for each Lambda's DB path, contract tests for the request/response shapes in internal/queries, and a pool load test before rollout.
